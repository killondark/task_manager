# Обсуждение перед изменениями

Правило работы в этом проекте: **сначала обсуждаем, потом вносим правки**.

## Как работать

1. **Сначала предложи.** Когда нужно что-то изменить (код, файлы, конфиг, документация, спеки), сначала опиши пользователю:
   - что собираешься сделать,
   - какие файлы затронешь,
   - в каком порядке будешь действовать.

2. **Дождись ответа.** Не вноси правки, пока пользователь явно не согласится. Пользователь читает твоё предложение и решает — согласиться или скорректировать.

3. **Только после одобрения — действуй.** Получив согласие, выполняй ровно то, что было согласовано. Не расширяй объём самовольно.

4. **Если объём меняется** в процессе — снова остановись и согласуй изменение плана.

## Что можно делать без согласования

- Читать файлы и исследовать код (read-only операции).
- Отвечать на вопросы пользователя.
- Выполнять явно данную команду вносить правки.

## Запуск dev-сервера

Если по ходу работы нужно запустить `bin/rails server` для проверки — **обязательно останови его после завершения проверки** (по аналогии с `Task 5.2: затем остановить сервер`). Не оставляй работающий `bin/rails server` после себя.

## Бизнес-логика: интеракторы, контракты, монады

Любая бизнес-логика (создание/обновление/удаление, мутации) размещается **в интеракторах**, а не в контроллерах и моделях.

- **Интеракторы** (`app/interactors/`) — `ApplicationInteractor` (наследует `Dry::Monads`, `Dry::Initializer`, содержит `BaseContract` и хелперы `validate_contract`, `process_error`). Конкретные операции: `Tasks::Creator`, `Tasks::Updater`, `Tasks::Destroyer` и т.д.
- **Контракты** — валидация входных данных через `Dry::Validation::Contract` (форма входа — типы, наличие обязательных полей). Валидация атрибутов остаётся в AR-модели как единый источник правил.
- **Результат** — `Success(task)` / `Failure(task)`, контроллер ветвляет по `success?` / `failure?`.
- **Для full-stack приложений** значение `Failure` — объект с `errors`, чтобы контроллер мог передать его обратно в форму (`@task = result.failure`).
- **Избегай** прямых мутаций AR в контроллерах, сервис-объектов на plain Ruby-классах и паттерна «толстая модель» — вся мутабельная логика в интеракторах.
